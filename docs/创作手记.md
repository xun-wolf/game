# 《田间风云》创作手记

**作品名称：** 田间风云（Field Chronicles）

**参赛方向：** AI 游戏作品 · 策略卡牌 × 种田经营

**作品试玩链接：** https://www.modelscope.cn/studios/xu0987/field-chronicles-xu0987

**演示视频：** 待补（建议 60–90 秒，录制要点见文末「附录」）

## 1. 创意与玩法

我想把「种地」这件事里的压迫感做成可玩的东西。玩法框架参考了 itch.io 独立游戏 Cardwork Cycle 的卡牌 × 种田组合，但把重心从「爽快收获」移到「扛过一年」：虫害、旱情、体力与岁赋同时压过来，玩家要在 24 个节气里把一年的收成撑到完税。

**一句话概括：** 24 候 = 一局，种、浇、除虫、卖粮、完税，活下来就算赢。

**每候的核心循环：**

1. 抽 5 张手牌、3 点体力，打出农事卡：开垦/播种、浇水、除虫、防护；
2. 作物按耗水推进生长阶段，成熟后收获二选一——卖粮换存银，或留种换卡牌；
3. 结束回合，推进一个节气。第 3/6/9/12/15/18/21 候各来一波虫潮，第 12 候「大暑修渠」强制扣银；
4. 第 24 候大寒完税，存银够即通关，不够则欠赋失败。

**四重压力设计：**

- **时令**：四季各 6 候，共 24 候，一局就是一年，终局倒计时明确；
- **虫害**：7 波按品级分档，单波虫量与血量随难度上升；三品、一品有固定虫王（12 血）；
- **旱情**：三品旱期 10–12 候、一品 10–14 候，大暑阶段作物耗水翻倍；
- **体力**：每候只有 3 点，种、浇、打虫互相挤占，必须取舍。

**五档官品 = 三维难度（税 + 虫 + 旱）：**

| 官品 | 岁赋 | 虫潮档位 | 开局接济 | 固定虫王 | 旱期 |
| :--- | ---: | :--- | ---: | :--- | :--- |
| 九品 · 丰年祥和 | 18 两 | mild | 0 | 无 | 无 |
| 七品 · 小有积蓄 | 24 两 | normal | 0 | 无 | 无 |
| 五品 · 勉力支撑 | 24 两 | severe | 0 | 无 | 无 |
| 三品 · 十室九空 | 24 两 | severe | 6 两 | 第 21 候 | 10–12 候 |
| 一品 · 神农绝境 | 32 两 | extreme | 6 两 | 第 18、21 候 | 10–14 候 |

**作品亮点：**

- **节气即回合**：立春到大寒，一年一局，规则与节奏一眼看懂；
- **收获二选一**：卖粮保现金流，还是留种收卡牌做长期牌库成长，是本作最核心的取舍；
- **隐藏结局**：小白菜收获 ≥6 次 / 番茄 ≥3 次 / 葡萄 ≥2 次后，下一次收获必出「百年月华·金稻」，种成即传奇胜利；
- **点开即玩**：纯前端静态包，无需登录、无后端依赖。

## 2. 创作过程

项目主体此前已由 AI 辅助完成初版；本次参赛周期内，我们把它从「能跑的工程」收敛成「可公开试玩、数值站得住、能上线」的完整作品。

**开发时间线（与仓库提交一致）：**

| 时间 | 主要工作 |
| :--- | :--- |
| 11-21 | 建立仓库，把项目纳入版本管理 |
| 11-23 | 完整 Godot 工程、策划文档、HTML 原型与平衡脚本统一进仓库；纠正文档与工程不一致（Godot 3.5.3、24 候、5 官品） |
| 11-25 | 开场四幕动画（农书墨痕 → 灯下成牌）；作物生长阶段点、悬停成熟提示；主菜单信息层级与布局修复 |
| 11-26 | 数值平衡 P0–P2：虫潮改为按品级分档的候级波次、商店定价统一为 12/20/32、金稻速生与门槛、第 12 候修渠、对局统计埋点、终局结算时序修复 |
| 11-27 | 导出 HTML5（GLES2）完整工程并做 Web 适配；制作 9 个尺寸的游戏封面与分层源文件；部署到魔搭创空间（Static）并线上实测通过 |

**人和 AI 的分工：**

- **我负责**：定方向、提需求、实机试玩、判断手感与难度、做取舍、执行部署；
- **AI 负责**：GDScript 实现、场景与 UI 调整、Python 生成贴图/音效与数值扫描、写文档、导出配置、部署排查；
- **协作方式**：我先描述「哪里不对 / 想要什么感觉」，AI 给出最小改动方案，我跑一局再决定保留或回退。所有数值改动都要先过自动测试，再进实机确认。

## 3. 工具应用与体验

- **Trae（AI IDE，主要开发环境）**：跨文件修改 GDScript（`GS.gd` 结算队列、`SeasonManager`、`DifficultyManager`）、批量改 `.tscn`、写导出预设、排查创空间部署。它能基于工程上下文给出成体系的改动；但手感和数值仍须实机跑局验证，我只保留跑通的部分。
- **Python（Pillow / 合成音频）**：程序化生成四档害虫立绘（`gen_bugs.py`）、中文标题与朱印（`gen_title_cn.py`）、四季粒子（`gen_season_fx.py`）与音效（`gen_bug_sfx.py`）；`balance_sim.py`、`drought_sweep.py`、`tier5_sweep*.py` 做数值扫描。改一版美术从小时级降到分钟级，数值扫描也能在进游戏前淘汰不可行的参数。
- **Godot 3.5.3（GLES2）**：主场景 `MainMenu.tscn`，`SeasonManager` / `DifficultyManager` / `GS` 等 Autoload 常驻管理状态，导出 HTML5 与 Windows。Web 版稳定、包体可控（`index.pck` 约 35.8MB）；需注意 3.x 与 4.x 的 API 差异（循环动画用 `set_repeat`）。
- **魔搭创空间（Static）**：上传 9 个文件，SDK 选 Static、入口 `index.html`、免费 CPU。不启 Python 进程，发布快且稳定；关键是 `.wasm` 的 MIME 为 `application/wasm`、资源全部用相对路径。
- **AI 文生图**：生成暮色稻田主视觉，配合 Pillow 合成 9 个尺寸并输出 `.ora` 分层源文件；适合「一张主视觉 + 多尺寸」，文字与构图仍需人工调整。
- **本次未使用**：Qoder、魔搭 API Inference、赞奇 / 华硕 DGX Spark 节点——本作是纯前端确定性规则游戏，不依赖在线推理或 GPU。

## 4. 问题与解决

**真实问题：第 24 候「明明有钱，却被判欠赋」。**

- **现象**：最后一批作物在第 24 候成熟，收获面板先弹出；完税结算 0.9 秒后就用「当前存银」判定，而这段时间卖粮的钱还没入账。玩家看到「存银 20 两、税 18 两」，结算却显示欠赋失败。
- **根因**：结算在「入队时」就固化了存银快照，而收获是异步队列，两者的执行顺序错了——先判定、后入账。
- **解决**：
  1. 新增 `final_tax` 队列项，只负责排队，不提前判定；
  2. 等轮到它真正显示时，再读取最新存银做判定（`GS.gd:162-167`）；
  3. 终局结算延迟 0.9 秒入队，保证收获与金稻胜利优先结算（`GS.gd:180-183`）；
  4. 补自动测试 `check_final_tax_timing()`：构造「存银 10 → 入队终局结算 → 卖粮 +10」，预期判「完税嘉奖」（`_devtest/autotest.gd:337-364`）。
- **效果**：测试输出 `终局时序: gold=20 tax=18 结算判定=完税嘉奖`；同一场景修复前会判失败。此后所有结算类改动都先跑 autotest，再实机确认。

**另外两个小坑：**

- Web 端执行 `OS.window_position` / 设置窗口标题会报错，导致导出版启动异常。用 `OS.has_feature("HTML5")` 守卫后解决，桌面端行为不变。
- 封面标题一度消失：裁切框按错误的画布尺寸计算，取到空白区域。改为按实际 1920×1080 定位裁切框，并让标题图层水平居中后恢复正常。

## 5. 经验总结

**可复用经验：**

1. **先做「能跑通的一局」，再做表现。** 顺序反了会反复返工——先确定 24 候、完税、收获这些规则能闭环，再叠开场动画和粒子。
2. **把关键规则写成自动测试场景。** 本项目用 `_devtest/autotest.gd` 覆盖五档难度、虫潮波次、金稻门槛、商店定价、结算时序，每次改动跑一遍并截图存档，比肉眼回归可靠得多。
3. **数值先模拟再上线。** 用脚本扫描税/虫/旱/定价的参数组合，先淘汰不可行的，再进游戏验证手感，能省掉大量「凭感觉改数字」的无效迭代。
4. **Web 导出三条硬约束**：资源用相对路径、`.wasm` 的 MIME 为 `application/wasm`、平台不支持的 API 加特性守卫。
5. **对 AI 的产出坚持「可验证」。** 每个改动都要有测试输出或截图证据；AI 说改好了不算，跑通才算。

**后续想改进的方向：**

- 统一卡面与音效的美术风格，补一套完整的卡牌原画；
- 增加随机农事事件与更多作物组合，提高重玩性；
- 移动端触控与横屏适配；
- 把已有的本地对局统计（`run_stats`）做成云端排行榜。
